# StyleFinder: спецификация лаборатории комнат

Статус: **draft для реализации и дизайнерской приёмки**  
Дата: **2026-07-23**  
Область: **мебельный планировщик прямоугольных комнат**

Связанные документы:

- [`stylefinder-remediation-spec.md`](./stylefinder-remediation-spec.md) — требования доверенного MVP;
- [`furniture-planner-plan.md`](./furniture-planner-plan.md) — архивный план исходного прототипа;
- `next/src/shared/lib/furniture-planner/golden-rooms.ts` — текущие исполняемые эталонные комнаты.

## 0. Коротко

Нужно сделать постоянную лабораторию, которая создаёт комнаты, запускает решатель,
проверяет результат автоматически и готовит планы для визуального просмотра.

Лаборатория должна отвечать не только на вопрос «план валиден?», но и на вопросы:

- мебель образует понятные функциональные зоны или случайно раскидана;
- объекты не собрались без причины в одном углу;
- диван, ТВ и столик работают как одна композиция;
- кровать, тумбы и хранение образуют спальню;
- стол действительно использует окно, а книжный шкаф относится к рабочей зоне;
- варианты отличаются по структуре, а не сдвигом на несколько сантиметров;
- удаление предмета оправдано всем комплектом, а не названо ложной
  «несовместимостью» отдельного объекта;
- объяснение программы соответствует показанному плану.

Автоматика не должна изображать из себя дизайнера. Она проверяет доказуемые правила,
считает понятные метрики и поднимает флаги. Итоговую оценку композиции для
эталонных комнат подтверждает человек.

## 1. Цель

Создать воспроизводимый цикл улучшения планировщика:

1. создать или импортировать комнату;
2. построить до трёх вариантов;
3. проверить жёсткую геометрию и функциональные связи;
4. посчитать признаки качества;
5. отрисовать одинаковые превью;
6. поставить оценку `хорошо / допустимо / спорно / плохо`;
7. сохранить конкретную причину;
8. превратить подтверждённую ошибку в регрессионный кейс;
9. повторить весь набор после изменения алгоритма.

В итоге любое изменение решателя должно показывать, какие комнаты стали лучше,
какие не изменились и где появилась регрессия.

## 2. Что именно проверяем

### 2.1. Корректность

Это бинарный слой. Здесь нет вкусовой оценки.

- корпус и обязательные зоны находятся внутри комнаты;
- нет запрещённых пересечений;
- дверь и зона открывания свободны;
- радиатор и его сервисная зона учтены;
- правила окна соблюдены;
- сохраняется проверяемый проход;
- обязательные связи мебели выполнены;
- ТВ направлен на выбранную цель;
- результат `success` повторно проходит `validateLayout`;
- `proven-impossible` выдаётся только после полного допустимого поиска;
- `search-exhausted` не называется доказанной невозможностью;
- автоматическое удаление затрагивает только `optional`;
- одинаковый ввод даёт одинаковый результат.

Любое нарушение этого слоя означает `fail`, даже если план визуально выглядит
нормально.

### 2.2. Функциональное качество

Этот слой частично автоматический.

- гостиная собирается вокруг одного дивана;
- ТВ и кофейный столик относятся к тому же дивану;
- тумбы относятся к выбранной кровати;
- комод находится в понятной близости к спальной зоне и не попадает к окну;
- книжный шкаф находится в понятной близости к рабочему столу;
- рабочий стол использует окно, если такой сценарий указан;
- в студии спальная, гостиная и рабочая зоны читаются отдельно;
- независимые зоны не смешиваются случайно;
- предмет не остаётся визуально и функционально «сиротой».

### 2.3. Композиционное качество

Этот слой автоматика только подсвечивает. Финальное решение принимает человек.

- нет необъяснимой свалки в одном углу;
- нет бессмысленного разбрасывания связанных предметов по разным углам;
- свободное пространство выглядит пригодным для использования;
- проход не только формально существует, но и читается на плане;
- крупные предметы не образуют визуальный барьер;
- хранение не выглядит случайно прилепленным;
- пропорции комнаты используются разумно;
- вариант имеет понятную идею;
- три варианта дают реальный выбор.

## 3. Основные принципы

1. Жёсткая ошибка не перекрывается высоким quality score.
2. Один общий «балл адекватности» не является источником истины.
3. Автоматические метрики должны иметь понятное физическое или композиционное
   значение.
4. Субъективный отзыв не становится hard-правилом без отдельного решения.
5. Эталонные кейсы не фиксируют случайные координаты, если важен смысл
   планировки.
6. Случайная генерация всегда использует сохранённый seed.
7. Любой найденный случай должен воспроизводиться одним идентификатором.
8. Неуспешный случай сохраняет вход, статус, частичную расстановку и объяснение.
9. Результаты разных версий алгоритма нельзя сравнивать без номера версии
   каталога и решателя.
10. Лаборатория не изменяет пользовательский проект и не использует production
    данные.

## 4. Границы первой версии

В первую версию входят:

- прямоугольные комнаты от `2400 × 2400` до `10000 × 10000 мм`;
- текущие ограничения на двери, окна и радиаторы;
- весь текущий каталог мебели;
- приоритеты `required`, `preferred`, `optional`;
- выбор цели ТВ;
- один результат и до трёх структурно разных вариантов;
- автоматическая проверка;
- PNG-превью и контактный лист;
- ручная оценка и список замечаний;
- детерминированная генерация дополнительных комнат.

Пока не входят:

- Г-образные и произвольные комнаты;
- 3D и фотореалистичная визуализация;
- оценка цвета, стиля и материалов;
- автоматический «AI-дизайнер» как судья качества;
- сравнение с реальными SKU;
- обучение модели на пользовательских данных;
- публикация лаборатории как пользовательской страницы.

## 5. Уровни набора комнат

### 5.1. Curated golden

Небольшой набор вручную продуманных комнат. Он запускается на каждом pull request.

Первая цель — `30` комнат. После стабилизации набор может вырасти до `50–80`, но
каждый кейс должен сохранять понятную цель. Бессмысленно добавлять сотни почти
одинаковых fixtures.

### 5.2. Реальные спорные случаи

Комнаты из отзывов дизайнера или пользователя.

Для каждого случая сохраняются:

- исходный скриншот или ссылка на него;
- точные размеры и комплект мебели;
- что именно показалось неправильным;
- ожидается ли один конкретный результат или допустим диапазон решений;
- итоговое решение по спору.

Реальный случай после подтверждения становится постоянным regression fixture.

### 5.3. Детерминированная матрица

Комнаты строятся из заранее заданных диапазонов размеров, пропорций, препятствий
и мебельных программ. Все комбинации имеют стабильные идентификаторы.

Матрица нужна для широкого покрытия, но не требует ручного просмотра каждого
результата на каждом запуске.

### 5.4. Seeded fuzz

Ночной или ручной прогон создаёт сотни комнат с фиксированными seed.

Цели:

- найти падение;
- найти недетерминированность;
- найти ложный `proven-impossible`;
- найти невалидный `success`;
- найти резкое ухудшение времени;
- собрать кандидатов для ручного просмотра.

Случайный кейс, который нашёл ошибку, сохраняется как обычный fixture и больше не
зависит от генератора.

## 6. Модель кейса

Предлагаемая структура:

```ts
type RoomLabCaseSource = "curated" | "real" | "generated" | "regression";

type RoomLabExpectedStatus =
  | "success"
  | "proven-impossible"
  | "search-exhausted"
  | "invalid-room"
  | "invalid-request"
  | "access-unverified";

interface RoomLabCase {
  id: string;
  title: string;
  description: string;
  source: RoomLabCaseSource;
  tags: string[];
  room: Room;
  instances: FurnitureInstance[];
  preferences?: LayoutPreferences;
  requestedVariants: 1 | 2 | 3;
  expectation: {
    allowedStatuses: RoomLabExpectedStatus[];
    requiredPredicates: RoomLabPredicate[];
    forbiddenFindings?: RoomLabFindingCode[];
    expectedRemoval?: {
      allowedDefinitionIds: string[];
      maximumCount: number;
    };
  };
  provenance?: {
    reference?: string;
    note?: string;
  };
}
```

Кейс хранит экземпляры мебели, а не только список `definitionId`. Иначе нельзя
проверить приоритеты, несколько одинаковых предметов и точный состав удаления.

### 6.1. Предикаты вместо точных координат

Основные ожидания задаются смысловыми предикатами:

```ts
type RoomLabPredicate =
  | { kind: "layout-valid" }
  | { kind: "all-selected-items-placed" }
  | { kind: "connected-access"; minimumMm: number }
  | { kind: "living-block-coherent" }
  | { kind: "sleep-block-coherent" }
  | { kind: "work-block-coherent" }
  | { kind: "desk-near-window"; maximumMm: number }
  | { kind: "dresser-away-from-window"; minimumMm: number }
  | { kind: "tv-faces-target"; target: "living" | "sleep" }
  | { kind: "tv-on-long-wall" }
  | {
      kind: "zones-separated";
      first: string;
      second: string;
      minimumMm: number;
    }
  | { kind: "variants-structurally-unique"; minimumCount: number }
  | { kind: "deterministic" }
  | { kind: "maximum-runtime"; milliseconds: number };
```

Точные `x/y` допустимы только для boundary-тестов, где проверяется конкретная
критическая координата.

## 8. Автоматический аудит

### 8.1. Hard checks

Для каждого результата `success`:

- количество размещённых предметов совпадает с ожидаемым;
- каждый `instanceId` присутствует один раз;
- `validateLayout` возвращает `valid`;
- обязательные связи выполнены;
- нет запрещённого удаления;
- сохранён выбранный target ТВ;
- explanation не противоречит геометрии;
- сериализация результата не меняет координаты;
- повторный запуск даёт тот же semantic и structural signature.

Для failure-результатов:

- статус входит в `allowedStatuses`;
- сообщение соответствует статусу;
- `search-exhausted` не предлагает удаление;
- диагностический список не называется доказанной причиной;
- `proven-impossible` воспроизводится с полным бюджетом;
- минимальность удаления проверяется отдельным перебором допустимых optional-групп.

### 8.2. Функциональные метрики

Метрики считаются отдельно по блокам:

- `livingCompositionScore`;
- `sleepStorageCohesion`;
- `workStorageCohesion`;
- расстояние ТВ до цели;
- поперечное смещение ТВ и цели;
- расстояние столика до дивана;
- расстояние тумбы до кровати;
- расстояние комода до ближайшей кровати;
- расстояние книжного шкафа до стола;
- расстояние рабочего стола до подходящего окна;
- расстояние между центрами функциональных зон.

Если в комнате нет соответствующего блока, метрика имеет статус `not-applicable`,
а не ноль.

### 8.3. Автоматические quality flags

Флаги не проваливают тест сами по себе:

```ts
type RoomLabFindingCode =
  | "corner-pile"
  | "zone-scatter"
  | "orphan-item"
  | "oversized-empty-region"
  | "center-barrier"
  | "weak-tv-axis"
  | "storage-outside-zone"
  | "variants-too-similar"
  | "explanation-mismatch"
  | "asset-geometry-mismatch"
  | "unreasonable-removal"
  | "false-incompatibility"
  | "runtime-regression";
```

Правила первой версии:

- `corner-pile`: центры всех независимых функциональных блоков попали в один
  угловой сектор, при этом большая часть комнаты не используется;
- `zone-scatter`: члены одного блока имеют чрезмерный bounding box относительно
  площади их корпусов;
- `orphan-item`: предмет блока находится далеко от всех допустимых anchors;
- `oversized-empty-region`: крупная непрерывная часть комнаты пустует, а предметы
  при этом создают тесный кластер;
- `center-barrier`: крупные корпуса образуют поперечный барьер между дверью и
  устойчивыми зонами комнаты;
- `weak-tv-axis`: связь формально валидна, но поперечное смещение близко к
  допустимой границе;
- `variants-too-similar`: structural signature совпадает или меняется только
  один второстепенный предмет;
- `explanation-mismatch`: текст говорит о длинной стене, окне или зоне, но
  соответствующий предикат не выполнен;
- `asset-geometry-mismatch`: пользовательское изображение заметно выходит за
  расчётный корпус, имеет неверную ориентацию или создаёт ложное визуальное
  пересечение;
- `unreasonable-removal`: предложен более ценный optional-предмет, хотя
  существует доказанный вариант с меньшей потерей;
- `false-incompatibility`: интерфейс приписывает проблему одному предмету, хотя
  доказан только конфликт полного комплекта.

Порог каждого флага хранится рядом с его формулой и покрывается boundary-тестами.

### 8.4. Разнообразие вариантов

Для набора из трёх вариантов проверяются:

- semantic signature;
- structural signature;
- стена основных anchors;
- ориентация ТВ-зоны;
- расположение функциональных зон по половинам или квадрантам комнаты;
- свободный центр;
- профиль, который реально объясняет отличие.

Перемещение мебели вдоль той же стены не считается новой топологией само по себе.

## 9. Ручная оценка

### 9.1. Вердикт

```ts
type RoomLabVerdict = "good" | "acceptable" | "questionable" | "bad";
```

- `good` — вариант можно показывать без существенных замечаний;
- `acceptable` — вариант рабочий, есть небольшие компромиссы;
- `questionable` — технически валиден, но решение спорное и требует обсуждения;
- `bad` — план нельзя показывать пользователю как нормальный результат.

### 9.2. Оси оценки

Каждая ось получает `0`, `1` или `2`:

| Ось                   | `0`                              | `1`                   | `2`                               |
| --------------------- | -------------------------------- | --------------------- | --------------------------------- |
| Функциональная логика | связь непонятна или ошибочна     | работает с оговоркой  | связь очевидна                    |
| Зонирование           | зоны смешаны или раскиданы       | читаются частично     | зоны читаются сразу               |
| Баланс комнаты        | свалка или бессмысленные пустоты | допустимый компромисс | пространство использовано понятно |
| Проходы визуально     | выглядят заблокированными        | погранично            | движение читается                 |
| Полезность варианта   | нет самостоятельной идеи         | отличие небольшое     | вариант даёт реальный выбор       |

Сумма помогает сортировать комнаты, но не заменяет вердикт и комментарий.

### 9.3. Запись review

```ts
interface RoomLabManualReview {
  caseId: string;
  variantId: string;
  verdict: RoomLabVerdict;
  axes: {
    functionalLogic: 0 | 1 | 2;
    zoning: 0 | 1 | 2;
    roomBalance: 0 | 1 | 2;
    visualCirculation: 0 | 1 | 2;
    variantValue: 0 | 1 | 2;
  };
  findings: Array<{
    code: RoomLabFindingCode | "other";
    severity: "blocking" | "major" | "minor" | "question";
    instanceIds?: string[];
    comment: string;
  }>;
  caseFingerprint: string;
  layoutFingerprint: string;
  semanticSignature: string;
  structuralSignature: string;
  algorithmVersion: string;
  catalogVersion: string;
  reviewedAt: string;
  reviewerRole: "designer" | "product" | "engineering";
}
```

Комментарий обязателен для `questionable`, `bad` и любой оценки `0`.

### 9.4. Хранение review

Review хранится в Git отдельно от сгенерированного отчёта:

```text
next/src/shared/lib/furniture-planner/room-lab/reviews/<case-id>.json
```

Статический contact sheet не получает скрытый доступ на запись в репозиторий.
Кнопка review формирует и скачивает JSON. Отдельная команда валидирует файл,
сверяет fingerprints и только после явного запуска переносит его в `reviews/`.

Если изменился вход комнаты, layout fingerprint, semantic signature, structural
signature, версия каталога или алгоритма, review помечается `stale`. Старый
комментарий сохраняется как история, но больше не считается действующей
приёмкой.

## 10. Визуальный просмотр

Для каждой комнаты формируются:

1. план без служебных зон;
2. тот же план со служебными зонами;
3. геометрический контур поверх пользовательских изображений мебели;
4. до трёх вариантов в одинаковом масштабе;
5. подписи предметов и функциональных блоков;
6. автоматические флаги;
7. объяснение варианта;
8. статус поиска, время и число просмотренных узлов.

Отдельный geometry overlay нужен, чтобы отличать ошибку решателя от ошибки
ассета: изображение может быть сдвинуто, обрезано или визуально ориентировано не
так, как его расчётный корпус.

### 10.1. Контактный лист

Основной артефакт ручной проверки — HTML contact sheet:

- одна строка на комнату;
- варианты расположены рядом;
- масштаб одинаковый внутри одной комнаты;
- фильтры по тегу, вердикту, finding и статусу;
- переключатель hard/preferred зон;
- поле review;
- ссылка на полный JSON кейса.

PNG отдельных вариантов нужны для комментариев и истории, но не должны
бесконтрольно коммититься в Git.

### 10.2. Сравнение версий

При сравнении двух версий показываются:

- старый и новый план рядом;
- изменение hard status;
- изменение predicates;
- добавленные и исчезнувшие findings;
- изменение structural signature;
- изменение времени;
- прежний review и необходимость повторной оценки.

Если structural signature или состав удаления изменился, прежний ручной verdict
считается `stale`.

## 11. Как разбираем споры

1. Сначала фиксируем точный кейс и конкретное замечание.
2. Определяем тип: hard-ошибка, функциональная ошибка, вкусовое предпочтение или
   неполное исходное правило.
3. Проверяем источник правила мебели.
4. Не меняем глобальный score из-за одного скриншота.
5. Создаём минимум один контрпример, чтобы новая правка не ухудшила другую
   комнату.
6. Если мнения расходятся, кейс получает `questionable`, а не искусственный
   `pass`.
7. Новое hard-правило требует подтверждённого источника.
8. После решения сохраняем короткий rationale рядом с fixture.

Решения дизайнера имеют приоритет в композиционной оценке. Решения по
доказательности поиска, безопасности проходов и статусам ошибок остаются
инженерными.

## 12. Генерация комнат

### 12.1. Размеры и пропорции

Генератор покрывает:

- маленькие комнаты `5.8–12 м²`;
- средние `12–20 м²`;
- большие `20–35 м²`;
- очень большие `35+ м²`;
- почти квадратные, обычные и вытянутые пропорции;
- граничные размеры MVP.

Пропорции распределяются по buckets, а не выбираются полностью случайно:

- `square`: `1.0–1.2`;
- `regular`: `1.2–1.6`;
- `long`: `1.6–2.5`.

### 12.2. Проёмы и отопление

Сценарии:

- без препятствий;
- дверь по центру стены;
- дверь у угла;
- окно напротив двери;
- два окна на одной стене;
- окна на соседних стенах;
- радиатор под окном;
- радиатор на отдельной стене;
- препятствия возле соседнего угла;
- намеренно некорректные пересечения для negative tests.

Положительный генератор обязан сначала создать валидную геометрию комнаты.
Невалидные проёмы допускаются только в явно негативной группе.

### 12.3. Мебельные программы

- спальня;
- гостиная;
- рабочая комната;
- спальня-гостиная;
- студия с рабочим местом;
- детская с люлькой;
- хранение с разными шкафами;
- полный стресс-набор;
- набор с optional-предметами для проверки removal.

Количество мебели ограничивается catalog manifest. Генератор не имеет права
создавать невозможный `instanceId` или превышать `maxCount`.

### 12.4. Воспроизводимость и minimization

Каждый generated-кейс хранит:

- seed;
- версию генератора;
- все входные данные;
- версию каталога;
- версию алгоритма.

После finding генератор пытается уменьшить кейс:

1. убрать несущественные предметы;
2. убрать лишние проёмы;
3. уменьшить комнату до ближайшей границы, на которой проблема сохраняется;
4. сохранить минимальный воспроизводимый fixture.

Minimization не должен менять тип найденной ошибки.

## 13. Артефакты запуска

Один запуск создаёт:

```text
next/test-results/planner-room-lab/<run-id>/
  report.json
  summary.md
  contact-sheet.html
  cases/
    BR-01/
      input.json
      result.json
      variant-balanced.png
      variant-scenario.png
      variant-open-center.png
      debug-clearances.png
```

`report.json` содержит:

- commit SHA;
- algorithm version;
- catalog source hashes;
- Node и browser version;
- seed;
- время начала;
- список кейсов;
- результаты predicates;
- findings;
- runtime;
- semantic и structural signatures;
- ссылку на ручной review, если он существует.

Каталог `test-results` остаётся временным CI-артефактом. В Git хранятся fixtures,
review и только специально утверждённые reference-изображения.

## 14. Предлагаемая структура кода

```text
next/src/shared/lib/furniture-planner/room-lab/
  types.ts
  cases/
    curated.ts
    regressions.ts
  reviews/
    <case-id>.json
  predicates.ts
  metrics.ts
  findings.ts
  generator.ts
  minimize.ts
  evaluate.ts
  report.ts

next/src/shared/lib/furniture-planner/room-lab.test.ts
next/e2e/planner-room-lab.spec.ts
next/scripts/planner-room-lab.ts
```

Команды:

```text
npm run planner:lab:check
npm run planner:lab:render
npm run planner:lab:new -- --id <case-id> --from <input.json>
npm run planner:lab:fuzz -- --seed <seed> --cases <count>
npm run planner:lab:compare -- --before <report> --after <report>
npm run planner:lab:review -- --import <review.json>
```

CLI не должен дублировать solver. Он вызывает те же публичные функции, что и
пользовательский планировщик.

`planner:lab:new` создаёт черновой кейс из явного JSON или экспортированного
planner draft. Черновик не входит в CI, пока ему не назначены expectation,
provenance и стабильный ID.

Визуальный renderer должен использовать ту же геометрию и те же assets, но не
обязан поднимать весь пользовательский workflow.

## 15. CI

### На каждый pull request

- schema и уникальность ID всех fixtures;
- 30 curated/regression комнат;
- все hard predicates;
- детерминированность;
- отсутствие новых blocking findings;
- unit-тесты метрик на границах;
- typecheck, lint, format и build.

PNG на каждом PR не сравниваются pixel-by-pixel: такие snapshots слишком
чувствительны к браузеру и шрифтам. Вместо этого CI сохраняет contact sheet как
артефакт при изменении solver, geometry, catalog или room-lab.

### Ночью

- расширенная детерминированная матрица;
- `500–1000` seeded generated cases;
- проверка времени и памяти;
- рендер выборки с новыми findings;
- сохранение seed любого падения.

### Перед релизом

- все curated комнаты hard-green;
- нет `bad`;
- каждый `questionable` имеет решение или явно принятую оговорку;
- дизайнер просмотрел положительные эталонные комнаты;
- реальные спорные случаи повторно проверены;
- нет ухудшения удаления и честности failure-статусов;
- итоговый contact sheet приложен к release evidence.

## 16. Процесс после найденной проблемы

1. Лаборатория сохраняет case ID, вход и finding.
2. Человек подтверждает, что проблема реальна.
3. Кейс переводится в `regression`.
4. До исправления добавляется падающий смысловой predicate или тест метрики.
5. Вносится минимальная общая правка алгоритма.
6. Прогоняются все curated и regression комнаты.
7. Сравниваются старый и новый contact sheet.
8. Review обновляется только для реально изменившихся вариантов.
9. В rationale записывается, почему новая логика лучше и какие контрпримеры
   проверены.

Нельзя исправлять плохую комнату ценой молчаливого ухудшения нескольких других.

## 17. Этапы реализации

### Этап 1. Исполняемая основа

- тип `RoomLabCase`;
- предикаты hard/functional;
- перенос текущих 10 golden rooms;
- добавление оставшихся 20 curated cases;
- JSON-отчёт;
- единая команда `planner:lab:check`.

### Этап 2. Метрики качества

- block cohesion;
- orphan distance;
- block spread;
- corner pile;
- free-space balance;
- variant topology;
- explanation consistency;
- boundary-тесты всех порогов.

### Этап 3. Визуальный аудит

- общий plan renderer;
- PNG вариантов;
- debug-слой;
- HTML contact sheet;

### Этап 4. Генератор

- размерные buckets;
- программы мебели;
- валидные препятствия;
- fixed seed;

### Этап 5. Сравнение и CI

- diff двух запусков;
- stale reviews;
- PR artifacts;
- nightly fuzz;
- release evidence.

## 18. Критерии готовности лаборатории

Лаборатория считается рабочей, когда:

1. Все 30 первых комнат имеют стабильный ID и понятную цель.
2. Положительный `success` всегда повторно проходит общий валидатор.
3. Для каждой функциональной программы есть хотя бы один смысловой predicate.
4. Негативные статусы проверяются отдельно и честно.
5. Три варианта сравниваются по structural topology.
6. Любой finding содержит case ID и воспроизводимый вход.
7. Ручная оценка сохраняется отдельно от автоматических метрик.
8. Изменившийся вариант делает старую оценку устаревшей.
9. Contact sheet позволяет просмотреть 30 комнат без ручного ввода данных.
10. Один подтверждённый плохой кейс можно превратить в regression fixture без
    изменения production-кода.
11. PR-проверка не использует случайный seed.
12. Nightly failure сохраняет seed и минимальный воспроизводимый пример.

## 19. Решения, которые нужно подтвердить до визуального этапа

По умолчанию предлагается:

- начать с `30` curated rooms;
- хранить в Git fixtures и review, но не весь набор PNG;
- считать дизайнерский verdict главным для композиции;
- не использовать pixel snapshots как release gate;
- запускать `500` generated cases ночью и увеличивать число после измерения
  времени;
- сначала собрать runtime baseline, затем зафиксировать отдельные performance
  budgets для простых и сложных комнат;
- не открывать лабораторию в production.

Если эти решения принимаются, реализацию можно начинать с этапа 1 без
дополнительного проектирования.

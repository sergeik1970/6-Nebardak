# Админка: план

Цель — один закрытый раздел `/admin`, через который владелец следит за
пользователями, проектами и воронкой, состоянием сервера и разбором
расстановок, и выполняет основные действия с аккаунтами. Раздел живёт в
текущем Next-приложении и ходит в тот же API: те же cookie-сессии, CSRF,
ограничения частоты и деплой.

## Принципы

- **Права проверяет API.** Фронтенд только прячет то, что API всё равно не
  отдаст. Каждый маршрут `/api/admin/*` закрыт `AuthEnabledGuard`,
  `AuthGuard` и `AdminGuard`.
- **Вход администратора — пароль и код из письма.** Сессия без кода в
  админку не пускает (`user_session.second_factor_at`). Браузер, где код
  уже вводили, 30 дней входит по одному паролю.
- **Роль не выдаётся из интерфейса.** Только `admin:grant` на сервере.
- **Каждое изменяющее действие пишется в журнал аудита** (этап 2): кто, что,
  над кем, когда, с какого адреса. Журнал только дописывается.
- **Минимум персональных данных.** Списки показывают то, что нужно для
  решения; почта видна в карточке пользователя, в логах — только `userId`.
- **Разрешения, а не одна роль** (этап 2): таблица «роль → разрешения»
  (`users.read`, `users.manage`, `observations.triage`, `system.read`, …) и
  декоратор `@RequirePermission(...)`. Сегодня есть одна роль `admin` со всеми
  разрешениями; модератор очереди расстановок добавляется строкой в таблице.

## Этап 1. Вход администратора с кодом — сделан

- `POST /api/auth/login` для администратора не создаёт сессию, а отправляет
  шестизначный код и возвращает `{ user: null, secondFactor: { challenge,
  expiresAt } }`.
- `POST /api/auth/login/code` `{ challenge, code }` — сессия с отметкой
  второго фактора. 400 — неверный код (с остатком попыток), 410 — код
  истёк, использован или попытки кончились.
- Таблица `login_challenge`: хеш токена, HMAC кода с ключом-токеном, счётчик
  попыток. 10 минут, 5 попыток, один активный код на аккаунт, атомарные
  условные `UPDATE`/`DELETE`. Чистится вместе с прочими токенами.
- Сессия администратора: 7 дней без активности, не дольше 30 дней.
- Сброс пароля администратора не открывает сессию; `admin:grant` завершает
  все сессии аккаунта.
- Доверенное устройство: после верного кода браузер получает cookie
  `__Host-sf_trusted_device` (httpOnly, 30 дней от ввода кода, не
  продлевается). Пока она действует, пароль этого администратора открывает
  сессию с отметкой второго фактора без письма. В таблице `trusted_device`
  только хеш токена, не больше 10 устройств на аккаунт. Все устройства
  забываются при «выйти везде», смене и сбросе пароля и `admin:grant`;
  обычный выход устройство не забывает.
- Ограничение: код приходит на ту же почту, через которую сбрасывается
  пароль, поэтому он защищает от утечки пароля, но не от захвата почты.
  Следующий шаг при необходимости — TOTP-приложение для администратора.

## Этап 2. Каркас, обзор, пользователи

- Общий layout `/admin` с меню; очередь расстановок переезжает в него.
- `admin_audit_log` и страница журнала.
- **Обзор:** регистрации и подтверждения по дням, активные сессии, проекты
  по стадиям, новые расстановки на разбор.
- **Пользователи:** поиск и фильтры (подтверждён, роль, дата, активность),
  карточка: сессии (устройство, последняя активность), проекты, согласие.
  Действия: завершить сессии, заблокировать/разблокировать (`user.blockedAt`,
  проверка в `AuthGuard` и при входе), повторно отправить письмо, удалить
  аккаунт. Каждое — через журнал аудита и с подтверждением в интерфейсе.

## Этап 3. Сервер

- **Снимок на production:** systemd-таймер раз в минуту вызывает
  `stylefinder-status` и пишет JSON в каталог, смонтированный в `nest`
  только на чтение. Docker-сокет в API не пробрасывается.
- **История из монитора:** бот в Амстердаме раз в несколько минут отправляет
  на `/api/internal/monitor` (отдельный токен, не сессия) аптайм, сбои и
  перезапуски. Входящих портов на мониторе не нужно.
- Экран: контейнеры, диск, память, последний бэкап, сертификаты, аптайм за
  24 ч / 7 дней, лента сбоев.

## Этап 4. Воронка из Яндекс Метрики

- Цели уже отправляются: `test_start`, `test_complete`,
  `questionnaire_complete`, `room_drawn`, `layout_generated`,
  `layout_failed`, `plan_png_export`, `plan_print`, `drawing_file_save`,
  `signup`, `login`, `project_created`. Их нужно завести в интерфейсе
  Метрики как «JavaScript-событие» с теми же идентификаторами.
- Nest раз в час забирает агрегаты из Reporting API по OAuth-токену
  (`metrika:read`, хранится только в `.env.server`) и кеширует их; в браузер
  токен не попадает.
- Экран: воронка по шагам за период, разбивка по стилям, рядом — стадии
  сохранённых проектов из нашей базы.

## Что нужно от владельца

- Этап 1: выдать себе роль на сервере и проверить вход (см. `DEPLOY.md`).
- Этап 4: OAuth-токен Метрики и цели в интерфейсе счётчика.

# StyleFinder: спецификация доведения планировщика до доверенного MVP

Статус: **код доверенного MVP реализован и принят; публичный релиз заблокирован внешними gates**
Дата: **2026-07-17**
Ветка реализации: `codex/stylefinder-remediation`

## 0. Текущий итог реализации

Кодовые критерии спецификации закрыты и повторно проверены:

- frontend: `191/191` unit и `34/34` применимых browser E2E; `18` browser cases
  намеренно пропущены в проектах, для которых они не предназначены;
- backend: `64/64` unit и `7/7` HTTP security E2E;
- frontend и backend проходят format, lint, typecheck и production build;
- production dependency audit обоих приложений сообщает `0 vulnerabilities`;
- чистый production-like Docker-контур проходит миграции, повторное назначение
  least-privilege grants, healthchecks, runtime UID/capability и cache/header checks;
- независимый финальный аудит не нашёл оставшихся P0–P3 в коде.

Права на все 478 изображений подтверждены 2026-10-20
(`docs/image-rights/2026-10-20-owner-attestation.md`), release gate прав проходит.
Публикация пока запрещена. Перед ней обязательны смена раскрытых серверных доступов и переход на персональные SSH-ключи,
домен с HTTPS, off-site backup с restore drill, production monitoring, дизайнерская
приёмка эталонных комнат, проверка на реальных iOS/Android и выпуск из чистого
зафиксированного commit SHA через CI с container scan. Регистрация сохранена за
feature flags и в текущем релизе выключена.

## 1. Цель

Довести текущий прототип StyleFinder до состояния, в котором пользователь может:

1. определить визуальные предпочтения или пропустить этот шаг;
2. выбрать нужную мебель и назначить её важность;
3. точно описать прямоугольную комнату, дверь, окна и радиаторы;
4. получить до трёх действительно разных и проверенных вариантов;
5. понимать, какие ограничения проверены, а какие требуют ручной проверки;
6. безопасно изменить вариант вручную;
7. сохранить черновик и вернуться к нему после перезагрузки;
8. скачать план и спецификацию;
9. не передавать персональные данные, пока аккаунт не даёт реальной ценности.

## 2. Принципы реализации

- Все геометрические расчёты выполняются в целых миллиметрах.
- Корпус, обязательная свободная зона и желательная свободная зона — разные сущности.
- Успешный результат всегда повторно проходит общую валидацию.
- Неполный поиск не имеет права утверждать, что мебель физически не помещается.
- Автоматическое удаление не выполняется без предварительного показа и подтверждения.
- Реализация регистрации сохраняется в Git и выключается feature flag, а не закомментированным кодом.
- Состояние пользователя не теряется при обновлении страницы и возврате к предыдущему шагу.
- Интерфейс не использует слова «безопасный», «точно» и «невозможно», если это не доказано проверками.
- Новые типы комнат, 3D и расширение каталога начинаются только после приёмки прямоугольного ядра.

## 3. Границы доверенного MVP

В релиз входят:

- одна прямоугольная комната;
- одна дверь;
- до двух окон;
- до двух радиаторов;
- текущий каталог мебели;
- повороты с шагом 90°;
- ручное перемещение мебели с шагом 50 мм;
- до трёх семантически разных вариантов;
- локальное сохранение проекта;
- PNG, печатная версия и PDF;
- спецификация и оговорки решателя.

Не входят в этот релиз:

- Г-образные и произвольные комнаты;
- 3D;
- AI-генерация интерьера;
- реальные SKU, цены и остатки;
- совместное редактирование;
- облачные аккаунты и синхронизация;
- несколько дверей;
- произвольный угол поворота мебели.

## 4. Единый источник правил мебели

Для каждого определения мебели каталог обязан хранить:

- стабильный `definitionId`;
- пользовательское название;
- фактические части корпуса;
- обязательные свободные зоны;
- желательные свободные зоны;
- допустимые повороты;
- допустимые грани примыкания к стене;
- возможность расположения у окна;
- буфер от окна и штор;
- допустимые связанные предметы по `definitionId`;
- исключения пересечения зон связанных предметов;
- минимальные и рекомендуемые расстояния;
- симметричные повороты;
- максимальное количество;
- asset metadata и версию дизайнерского чертежа.

Документ дизайнера и runtime-каталог не должны существовать как две расходящиеся спецификации. Golden-тест обязан проверять runtime-каталог против утверждённого manifest.

Версия источников определяется содержимым, а не именем файла:

- `Мебель набор-Лист1.pdf` — SHA-256 `a51f5e4b64b615c0ba2df4ee3532241022ac7a4fa3c27a8850904f16c5f3627d`;
- `Нюансы мебелт.docx` — SHA-256 `e5c4545cbc94266fa095978edc80dd61599367fab05db31b000399b6b57dc45a`.

Замена любого файла требует нового хеша и осознанного обновления golden-manifest.

### 4.1. Обязательные исправления каталога

- Угловой диван: основной корпус `2200 × 950 мм`, шезлонг `730 × 550 мм`; точную форму служебной зоны подтвердить дизайнером.
- Люлька связывается только с двуспальной кроватью.
- Окно: привести список разрешённых предметов к утверждённой таблице.
- Реализовать утверждённый буфер 150 мм для штор после уточнения направления измерения.
- Кофейный столик не получает вымышленную собственную зону ради обхода общего валидатора.
- Тумба и кофейный столик используют явные relation exceptions.
- У мебели может быть несколько допустимых непунктирных граней примыкания.
- Круглые и симметричные предметы описывают эквивалентные повороты.

## 5. Геометрия комнаты

### 5.1. Валидация

Проверяются:

- положительные размеры комнаты в диапазоне MVP;
- попадание двери, окон и радиаторов в стену;
- пересечения препятствий на одной стене;
- двумерные пересечения зон препятствий на соседних стенах возле углов;
- сектор открывания двери;
- корпус радиатора как физическое препятствие и его свободная зона как запрет
  для мебели. Пустая свободная зона остаётся доступной для движения;
- окно и утверждённый буфер для штор.

Изменение размеров комнаты не должно молча обрезать размеры или координаты проёмов. Интерфейс показывает конфликт и предлагает явное исправление.

### 5.2. Честность приближений

Допустимые консервативные приближения MVP:

- круглый стол может проверяться bounding box;
- сектор двери может проверяться консервативной зоной.

Эти приближения должны быть описаны в результате. Они не должны называться точной инженерной проверкой.

## 6. Решатель

### 6.1. Генерация кандидатов

Фиксированные усечения координат заменяются критическими координатами:

- углы комнаты;
- края двери и сектора открывания;
- края окон и их буферов;
- края радиаторов и свободных зон;
- края уже размещённой мебели;
- края hard/preferred clearance;
- координаты примыкания каждой разрешённой гранью;
- сетка ручного шага как дополнительный, но не единственный источник.

Повороты сначала канонизируются по declared symmetry, после чего координаты
выдаются потоково. Декартовы произведения осей не материализуются целиком:
генерация кандидатов расходует тот же явный node budget, что и backtracking.
Если бюджет закончился до исчерпания потока, результат не может называться
`proven-impossible`.

Для обязательных связей `front-gap`, `adjacent` и `aligned-side` поток обязан
перебирать все разрешённые повороты и все целочисленные расстояния/смещения,
которые принимает валидатор. Если такой поток не исчерпан в пределах бюджета,
возвращается только `search-exhausted`, но не ложное доказательство
невозможности.

Неуказанные границы relation разрешаются одним общим правилом до генерации и
валидации: `front-gap` получает 350–450 мм, `adjacent` и `aligned-side` —
50–100 мм. Частично заданная граница заменяет только соответствующее значение
общего интервала.

Решатель возвращает один из статусов:

- `success` — найден и повторно проверен полный план;
- `proven-impossible` — отсутствие решения доказано полным допустимым поиском для данного режима;
- `search-exhausted` — лимит поиска исчерпан, отсутствие решения не доказано;
- `access-unverified` — физический дверной проём уже целевых 700 мм и
  доверенная проверка прохода недоступна;
- `invalid-room` — некорректна сама геометрия комнаты;
- `invalid-request` — нарушены связи или ограничения набора.

### 6.2. Оптимизация

Первый найденный план не считается автоматически лучшим. В пределах бюджета сравниваются допустимые планы по явным метрикам:

- отсутствие hard-конфликтов;
- сохранение preferred clearance;
- свободный связный проход;
- площадь свободного центра;
- качество целевых связей;
- близость рабочего стола к окну;
- компактность и читаемость композиции.

Названия «Больше света» и «Свободный центр» допустимы только если соответствующая метрика действительно оптимизируется. Иначе используются «Вариант 1–3».

### 6.2.1. Связный доступ от двери

Минимальная целевая ширина прохода MVP — `700 мм`: это минимальная величина,
которая повторяется в утверждённых служебных зонах кроватей, книжного шкафа,
тумбы, комода и диванов.

Hard-проверка строит конфигурационное пространство квадратного прохода и
проверяет связь двери со всеми устойчивыми участками комнаты, пригодными для
полных `700 мм`. Чтобы дискретизация не давала ложное `proven-impossible`,
доказательный проход намеренно уменьшен на одну envelope-ячейку `50 мм`, до
`650 мм`; препятствия раскладываются по их точным рёбрам, а переход по углу
разрешается. Поэтому проверка может пропустить пограничную тесноту шире 650,
но уже 700 мм. Реальный коридор ровно `700 мм` оставляет положительную полосу
шириной `50 мм` в доказательном пространстве и считается допустимой границей;
коридор `650 мм` уже находится за нижней границей допуска и отклоняется.

Допуск доказательного агента не применяется к физической ширине двери. Для
доверенного результата сам проём должен быть не уже `700 мм`; двери 600–699 мм
можно сохранить в параметрах комнаты, но решатель возвращает
`access-unverified` и не заявляет об успешной проверке 700 мм. Стартовые
ячейки ограничиваются центрами доказательного агента, которые действительно
проходят через указанный проём, а не расширенной зоной открывания двери.

Корпус радиатора участвует в конфигурационном пространстве как физическое
препятствие. Его сервисная/свободная зона по-прежнему запрещает размещение
мебели, но сама является пустым проходимым пространством.

### 6.3. Уникальность вариантов

Варианты считаются разными только при заметном геометрическом отличии. При сравнении канонизируются:

- перестановки одинаковых экземпляров;
- симметричные повороты;
- повороты круглых предметов;
- незначимые отклонения в пределах допуска.

Для MVP заметным считается евклидово перемещение хотя бы на `200 мм` — четыре
ручных шага по `50 мм`. Меньшее перемещение само по себе не создаёт новый
вариант; отличие несимметричного поворота остаётся заметным независимо от
координат.

### 6.4. Автоматическое удаление

- Не запускается после `search-exhausted`.
- Никогда не удаляет предмет с приоритетом `required`.
- В текущем MVP предложение рассматривает только предметы `optional`;
  `preferred` также не удаляются автоматически.
- Ищет минимальную стоимость удаления, а не первый предмет в списке.
- Сначала минимизируется количество удалённых предметов, затем потеря пользовательской полезности.
- До применения показывает пользователю список, объяснение и кнопку подтверждения.

## 7. Пользовательские приоритеты мебели

Каждый выбранный предмет получает один из приоритетов:

- `required` — не удалять автоматически;
- `preferred` — желательно сохранить;
- `optional` — можно предложить убрать.

Анкета предлагает разумные значения по умолчанию, но пользователь может изменить их. Программная логика не предполагает, что стол всегда менее важен, чем диван.

## 8. Сохранение проекта

Локальный draft хранит версионированный документ:

- результат и прогресс теста;
- ответы анкеты;
- приоритеты мебели;
- размеры комнаты;
- дверь, окна и радиаторы;
- выбранную цель ТВ;
- сгенерированные варианты;
- выбранный вариант;
- ручные координаты и повороты;
- дату изменения;
- версию схемы.

Требования:

- обновление страницы восстанавливает работу;
- «Изменить ответы» открывает заполненную анкету;
- устаревшая версия draft безопасно мигрирует или сбрасывается с объяснением;
- пользователь может начать новый проект явной кнопкой;
- сброс требует подтверждения.

## 9. Финальный результат

После выбора варианта пользователь получает:

- крупный план комнаты;
- PNG;
- печатную версию / PDF;
- размеры комнаты и проёмов;
- список мебели с габаритами;
- координаты и повороты;
- пользовательские приоритеты;
- удалённые предметы и причины;

- непроверенные или приближённые ограничения;

Облачная share-link является отдельным последующим этапом и требует backend.

## 10. Ручное редактирование

- Перетаскивание и стрелки проходят одну и ту же валидацию.
- Есть undo/redo.
- Есть отмена текущего перемещения.
- Ошибка отображается рядом с предметом и в панели проверки.
- На мобильном доступны fullscreen, zoom и pan.
- Удаление предмета и сброс проекта требуют подтверждения.

## 11. Тест визуальных предпочтений

- Случайность не участвует в SSR-разметке.
- Одна сессия использует детерминированный seed.
- Прогресс и seed сохраняются.
- Есть «назад», «оба», «ни один» и восстановление после перезагрузки.
- Пары распределяются симметрично.
- Ничья не зависит от позиции элемента в массиве.
- Названия сравниваемых категорий не показываются до результата.
- Результат содержит основной и близкие стили, уверенность, признаки, палитру и материалы.
- Тест позиционируется как тест визуальных предпочтений, пока методика не валидирована.
- Предзагружаются только текущий и ближайшие возможные следующие экраны.

## 13. Feature flags

Незавершённые функции не комментируются, а выключаются конфигурацией:

- `NEXT_PUBLIC_AUTH_ENABLED=false` — скрывает весь интерфейс аккаунта, очищает
  старую локальную сессию и запрещает клиентские auth-запросы;
- `NEXT_PUBLIC_AUTH_REGISTRATION_ENABLED=false` — при включённой авторизации
  оставляет только вход без текстов, полей и действий регистрации;
- `NEXT_PUBLIC_BETA_BADGE_ENABLED=true` — показывает честный статус beta;
- будущие серверные функции добавляются отдельными флагами.

Выключенная функция не должна оставлять интерактивные, но неработающие кнопки.

## 14. Производительность и ассеты

- Удалить неиспользуемые PNG из runtime-дерева и хранить исходники отдельно.
- WebP/AVIF должны иметь подходящее фактическое разрешение.
- Static assets получают fingerprint и immutable cache.
- Каталог изображений имеет manifest: decoded dimensions, точный alpha bounding
  box, encoded bytes, SHA-256, параметры кодирования, ориентация, back edge,
  версия и статус прав.
- Набор планировщика `2026-07-17-v2` содержит 15 WebP общей массой ровно
  1 316 024 байта при бюджете 1,4 МБ; CI сверяет manifest с реальными файлами,
  а не только с константами в TypeScript.
- Статус прав `unverified` является блокером публичного production-релиза:
  письменное подтверждение дизайнера сохраняется вне репозитория, а manifest
  после подтверждения получает ссылку на запись о происхождении/лицензии.
- Бюджет первого экрана теста на мобильной сети фиксируется performance-тестом.
- Не загружать весь набор изображений в фоне.

## 15. Backend и безопасность

До появления сохранённых облачных проектов публичная регистрация выключена.

Обязательный production baseline:

- фиксированные поддерживаемые версии runtime: Node.js 22.23.1, PostgreSQL 16.14
  на Alpine 3.24 и Caddy 2.10.2;
- HTTPS;
- same-origin `/api`;
- закрытый внешний порт Nest;
- отдельный deploy user и SSH-ключи;
- отключённый root/password SSH;
- firewall;
- non-root контейнеры: Caddy работает с эффективным UID/GID `10001:10001`,
  сохраняет только `NET_BIND_SERVICE`, а чистые `/data` и `/config` доступны ему
  для записи;
- секреты не входят в Docker build context;
- DTO и runtime validation;
- rate limiting;
- отдельные DB-роли;
- fail-fast для placeholder, коротких и совпадающих паролей DB-ролей;
- runtime-роль имеет DML только к `user`, `USAGE` только к `user_id_seq` и не
  имеет `TEMP`, schema DDL или доступа к migration history;
- controlled migration step;
- `/health/live` и `/health/ready`;
- off-site backup и проверка восстановления;
- structured logs, error tracking и uptime monitor;
- политика конфиденциальности до повторного включения аккаунтов.

## 16. Автоматические тесты

Детальная система генерации, автоматического аудита и ручной дизайнерской
приёмки комнат описана в
[`planner-room-lab-spec.md`](./planner-room-lab-spec.md).

### 16.1. Unit и golden

- manifest всех предметов совпадает с утверждённой спецификацией;
- каждый корпус и каждая зона корректно поворачиваются;
- матрица разрешений у окна;
- все допустимые грани стены;
- люлька только с двуспальной кроватью;
- тумба, столик и ТВ соблюдают связи;
- дверь, окно и радиатор проверяются на границах и в углах;
- ширина двери проверяется на 599/600/649/650/699/700/701 мм;
- пользовательские приоритеты сохраняются.

Исторический end-to-end fixture комнаты 10 000 × 2 400 мм не сохранил точные
проёмы и препятствия, поэтому спецификация не приписывает ему восстановленное
покрытие. Исправленный механизм защищён воспроизводимым unit-тестом: критическая
координата книжного шкафа `x=1500` и полный 50-мм grid должны сохраняться.

### 16.2. Property

- любой `success` проходит `validateLayout`;
- корпуса остаются в комнате;
- запрещённые пересечения отсутствуют;
- одинаковый ввод даёт одинаковый результат;
- малые сцены сравниваются с полным перебором;
- `search-exhausted` не превращается в доказанное отсутствие решения;
- auto-removal не удаляет required.

### 16.3. E2E

- главная → анкета → планировщик → варианты → ручная правка → PDF;
- тест предпочтений → анкета → планировщик;
- возврат в заполненную анкету;
- восстановление после reload;
- мобильный planner;
- keyboard-only сценарий;
- отсутствие hydration и console errors;
- accessibility smoke через axe.

## 19. Критерий готовности релиза

Релиз доверенного MVP разрешён, когда одновременно выполнено следующее:

1. Нет P0/P1 security findings в публичном контуре.
2. Все unit/golden/property/E2E проверки зелёные.
3. На одинаковом вводе результат детерминирован.
4. Не найдено ложных `no-layout` на корпусе малых exhaustive-сцен.
5. Дизайнер принял 20–30 эталонных комнат.
6. Пользователь может восстановить и экспортировать результат.
7. В интерфейсе видны все существенные оговорки.
8. Production работает через HTTPS и имеет проверенный backup.
9. Мобильный golden path проходит без блокирующих ошибок.
10. Нет hydration и uncaught console errors на публичных маршрутах.
11. Для каждого опубликованного дизайнерского изображения письменно подтверждено
    право использования; `unverified` asset отсутствует в публичном релизе.
    Все 478 текущих файлов перечислены по неизменяемому составу и SHA-256 в
    `next/image-rights.manifest.json`; `npm run assets:rights:release` является
    обязательным fail-closed gate. Выполнено 2026-10-20: все группы `cleared`
    по записи `docs/image-rights/2026-10-20-owner-attestation.md`.
12. На чистых Caddy volumes контейнер стартует с UID/GID `10001:10001`, может
    записывать ACME/config state и отвечает через опубликованные `80/443`, не
    получая capabilities кроме `NET_BIND_SERVICE`.
13. Все runtime-изображения имеют версию в пути: каталоги теста и планировщика
    версионированы, а 9 общих Home-изображений содержат 12-символьный SHA-256 в
    имени. Caddy выдаёт каждому из этих трёх классов единичный immutable
    `Cache-Control`, проверяемый container gate.

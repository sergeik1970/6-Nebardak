# План: аккаунты, облачные проекты и сквозной путь «тест → анкета → комната → расстановка»

Дата: 2026-10-20\
Статус: согласовано 2026-10-20, в работе\
Ветка: `feature/accounts-projects` (от `codex/stylefinder-remediation`)

## 1. Цель

Пользователь может зарегистрироваться, подтвердить почту и войти. Всё, что он
делает с проектом (тест стиля, анкета, чертёж комнаты, расстановка, ручные
правки), сохраняется в его аккаунте автоматически и открывается с любого
устройства. Без аккаунта сайт работает как сейчас, а локальный черновик
переносится в аккаунт при входе.

## 2. Согласованные решения

| Вопрос | Решение |
|---|---|
| Масштаб | Одна комната на проект. Модель данных не мешает позже перейти к квартире. |
| Гости | Работают без аккаунта, черновик в браузере; при входе/регистрации переносится в аккаунт. |
| Авторизация | Почта + пароль, подтверждение почты, сброс пароля. Без соцсетей. |
| Путь | Тест → анкета → рисование комнаты → расстановка → итог. Тест и анкета остаются в начале. |
| Проекты | Несколько на пользователя, страница «Мои проекты». |
| Сохранение | Автосохранение с индикатором; офлайн и две вкладки поддерживаются. История версий — не в этом релизе. |
| Дополнительно | Личный кабинет (имя, пароль, выход со всех устройств, удаление аккаунта). |
| Запуск | Публичный, без жёсткого срока, включая production-блокеры. |
| Юрисдикция | Пользователи и сервер в РФ → 152-ФЗ. |
| Почта | Абстракция SMTP; в dev — Mailpit, провайдер для prod выбирается позже. |

## 3. Что уже есть (исходное состояние)

- **Nest:** `register` / `login` / `me`, bcrypt cost 12, JWT HS256 24h, throttling,
  роли `designer` / `admin`, флаги `AUTH_ENABLED` и `REGISTRATION_ENABLED` (сейчас выключены).
- **Next:** `AuthContext`, `AuthModal`, токен и пользователь в `localStorage`, Bearer-заголовок.
- **Состояние проекта разбито на три независимых ключа `localStorage`:**
  - `stylefinder:project-draft:v4` — тест, анкета, комната, варианты, правки
    (`shared/lib/furniture-planner/project-draft.ts`, с нормализацией и миграциями v1→v4);
  - `stylefinder:draw-room-editor:v1` — сцена редактора (сегменты стен, проёмы,
    помещения, мебель редактора) в `shared/pages/DrawRoom/index.tsx`;
  - `stylefinder:draw-room-draft:v1` — передача комнаты из `/planner/draw` в `/planner?drawRoom=1`.
- Чертёж (сцена стен) **не входит** в project draft: туда попадает только производная `Room`.
  Значит, сейчас нельзя сохранить проект так, чтобы потом продолжить редактировать стены.
- `Planner/index.tsx` — ~8 000 строк, `DrawRoom/index.tsx` — ~6 300 строк; оба
  читают и пишут storage напрямую.
- Production: Caddy проксирует `/api/*` на Nest на том же origin — удобно для cookie.
  Runtime-роль БД имеет DML только к `user` и `planner_observations`.

## 4. Архитектура (целевая)

### 4.1. Сессии вместо JWT в localStorage

- После входа сервер выдаёт **непрозрачный** случайный токен (32 байта) в cookie
  `__Host-sf_session` с флагами `HttpOnly; Secure; SameSite=Lax; Path=/`.
  В dev без HTTPS — `sf_session` без `Secure` и без префикса `__Host-`.
- В БД хранится только SHA-256 хеш токена: таблица `user_session`
  (`id`, `user_id`, `token_hash` unique, `created_at`, `last_seen_at`, `expires_at`,
  `user_agent` усечённый, `ip` — не храним, чтобы не множить персональные данные).
- Срок 30 дней со скользящим продлением (обновлять `last_seen_at` / `expires_at`
  не чаще раза в час). Абсолютный предел — 90 дней.
- Почему не JWT в cookie: нужен мгновенный выход со всех устройств, отзыв сессий
  при смене/сбросе пароля и при удалении аккаунта.
- **CSRF:** `SameSite=Lax` + для всех изменяющих запросов (`POST/PUT/PATCH/DELETE`)
  проверка заголовка `Origin` (должен совпадать с `PUBLIC_ORIGIN`) и обязательного
  `X-Requested-With: stylefinder`. Отдельный guard, покрытый e2e-тестами.
- **Dev:** в `next.config.js` добавить `rewrites` `/api/* → http://localhost:3001/api/*`,
  чтобы dev тоже работал на одном origin. CORS в dev становится не нужен.
- `AuthGuard` читает cookie; Bearer-путь удаляется (включая админку наблюдений).
  Старые токены в `localStorage` фронтенд при старте молча удаляет.
- Эндпоинты: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`,
  `POST /auth/logout-all`, `GET /auth/me`.

### 4.2. Почта: подтверждение и сброс

- Таблица `email_token`: `id`, `user_id`, `purpose` (`verify-email` | `reset-password`),
  `token_hash` unique, `expires_at`, `used_at`, `created_at`.
  Срок: подтверждение — 48 ч, сброс — 1 ч. Одноразовые. Новый токен того же
  назначения аннулирует предыдущие.
- `MailService` с интерфейсом `send(message)`; реализация через `nodemailer` SMTP.
  Env: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`,
  `PUBLIC_ORIGIN`. В production при `AUTH_ENABLED=true` без SMTP — fail-fast на старте.
- В `docker-compose.dev.yml` добавить Mailpit (SMTP 1025, UI 8025). E2E читают
  письма через API Mailpit.
- Письма на русском, plain text + простой HTML, без внешних картинок и трекинга.
- Эндпоинты:
  - `POST /auth/verify-email` `{ token }`;
  - `POST /auth/resend-verification` (для вошедшего; throttle 3 / 15 мин);
  - `POST /auth/forgot-password` `{ email }` — **всегда** 202, одинаковое время
    ответа (защита от перечисления email); throttle по IP и по email;
  - `POST /auth/reset-password` `{ token, password }` — меняет пароль, отзывает
    **все** сессии, помечает почту подтверждённой (владение доказано), сразу логинит.
- Ссылки в письмах ведут на frontend: `/auth/verify?token=…`, `/auth/reset?token=…`;
  страница сама отправляет POST (GET-ссылка не меняет состояние, чтобы почтовые
  сканеры не «съедали» токен).
- Неподтверждённый аккаунт может работать и сохранять проекты; в шапке баннер
  «Подтвердите почту» с повторной отправкой. Неподтверждённые аккаунты без
  входов 30 дней удаляются фоновой задачей (см. §4.6).
- Существующие аккаунты с bcrypt cost < 12 теперь получают рабочий путь — сброс пароля.

### 4.3. 152-ФЗ и личный кабинет

- Регистрация: отдельный обязательный чекбокс согласия на обработку ПДн со ссылкой
  на текст согласия; ссылка на политику конфиденциальности. В `user` хранить
  `consent_version` и `consent_at`.
- Страницы `/privacy` и `/consent`. Я подготовлю черновик текстов по фактическим
  данным (email, имя, проекты, cookie сессии, логи), **но финальную редакцию
  должен проверить юрист**.
- Действия владельца (не код): уведомление Роскомнадзора об обработке ПДн,
  сервер и бэкапы в РФ.
- `/account`:
  - имя — изменить;
  - email — показать статус подтверждения (смену email отложить на следующий релиз);
  - пароль — сменить (требует текущий; отзывает остальные сессии);
  - «Выйти на всех устройствах»;
  - «Удалить аккаунт» — с вводом пароля; каскадно удаляет сессии, токены, проекты,
    наблюдения планировщика; ответ — выход и сообщение.
- В логах не писать email и тела проектов; только `user_id` и коды событий.

### 4.4. Облачные проекты (backend)

Таблица `project`:

| Поле | Тип | Примечание |
|---|---|---|
| `id` | uuid | генерируется сервером, в URL |
| `owner_user_id` | int FK → user, `ON DELETE CASCADE` | индекс `(owner_user_id, updated_at desc)` |
| `name` | varchar(80) | «Проект 1», редактируемое |
| `document` | jsonb | см. §4.5 |
| `document_version` | smallint | версия схемы документа |
| `revision` | int | +1 при каждом сохранении, для оптимистичной блокировки |
| `client_import_id` | varchar(64) null | идемпотентность импорта гостевого черновика, unique с владельцем |
| `summary` | jsonb | лёгкие поля для списка: стиль, площадь, кол-во мебели, этап |
| `created_at`, `updated_at` | timestamptz | |

API (всё под `AuthGuard`, владелец проверяется **в каждом запросе** — запрос
чужого `id` даёт 404, не 403):

- `GET /projects` — список без `document` (id, name, summary, updated_at, revision).
- `POST /projects` `{ name?, document?, clientImportId? }` → 201; повтор с тем же
  `clientImportId` возвращает уже созданный проект.
- `GET /projects/:id` → полный проект.
- `PUT /projects/:id/document` `{ document, baseRevision }` → `{ revision, updatedAt }`;
  если `baseRevision` устарел — 409 с текущими `revision` и `updatedAt`.
- `PATCH /projects/:id` `{ name }`.
- `POST /projects/:id/duplicate`.
- `DELETE /projects/:id` (с подтверждением на фронте).

Ограничения: не больше 50 проектов на пользователя; `document` ≤ 1 МБ (лимит
body-parser для этих маршрутов поднять до 1.1 МБ, глобально оставить маленький);
throttle на `PUT` — 60/мин на пользователя.

Валидация на сервере — **конверт**: объект, `version` из допустимых, известные
ключи верхнего уровня, глубина/размер. Полная доменная нормализация остаётся
на клиенте (уже есть, с миграциями), потому что документ влияет только на
своего владельца и рендерится React без `innerHTML`. Если позже понадобится
серверная обработка документа (шаринг, рендер PDF), доменный модуль выносится
в общий пакет.

Инфраструктура: миграции TypeORM; в `infra/postgres/provision-db-roles.sh`
добавить DML-права на `user_session`, `email_token`, `project` (+ последовательности),
обновить `verify-migrations.sh` и тест прав роли.

### 4.5. Единый документ проекта v5 (frontend)

Сейчас состояние разорвано на три ключа. Вводим один документ:

```ts
interface StyleFinderProjectDocument {
  version: 5;
  updatedAt: number;
  visualTest?: VisualTestSession;          // как в v4
  questionnaire: { items; preferences?; meta? }; // как в v4
  drawing?: DrawingProjectScene;           // НОВОЕ: сегменты, проёмы, помещения, толщина стен
  planner?: { room; selection; priorities; preferences?; layout?; designLab?; removedItems?; removalArchive? };
}
```

- `normalizeProjectDraft` расширяется до v5; v1–v4 мигрируют (у v4 `drawing` пуст,
  но при наличии `stylefinder:draw-room-editor:v1` сцена подтягивается из него однократно).
- `draw-room-draft:v1` (передача комнаты) упраздняется: комната берётся из
  `drawing` в том же документе. Ключ остаётся читаемым одну версию для миграции.
- Валидатор сцены — существующий `parseDrawingProject` из `DrawRoom/project-file.ts`
  (переносится в `shared/lib/furniture-planner`).

**Хранилище — через репозиторий, а не напрямую:**

```ts
interface ProjectRepository {
  list(): Promise<ProjectSummary[]>;
  load(id): Promise<LoadedProject>;
  create(input): Promise<LoadedProject>;
  saveDocument(id, document, baseRevision): Promise<SaveResult>; // ok | conflict | offline | error
  rename / duplicate / remove
}
```

- `LocalProjectRepository` — гость: один проект `local` в `localStorage` (текущий формат ключа v5).
- `RemoteProjectRepository` — вошедший пользователь: API + локальный кэш
  `stylefinder:project-cache:<id>` (последняя подтверждённая версия + неотправленные изменения).

**`ProjectProvider` (React context)** — единственная точка доступа к проекту для
Test, Questionnaire, DrawRoom и Planner:

- `project`, `document`, `update(mutator)`, `saveState`, `flush()`;
- текущий проект определяется query-параметром `?project=<uuid>` (гость — без
  параметра). Query, а не `/projects/[id]/…`, чтобы не ломать режим `NEXT_OUTPUT=export`.

Это самый объёмный рефакторинг: в Planner и DrawRoom надо заменить прямые вызовы
`saveProjectDraft` / `readProjectDraft` / `readDrawRoomDraft` / editor-session на провайдер, не
меняя их внутреннюю логику. Попутно из `Planner/index.tsx` выносится
слой загрузки/сохранения в отдельный хук (`usePlannerPersistence`) — полный
распил 8 000 строк в этот план не входит.

### 4.6. Автосохранение

Машина состояний `idle → dirty → saving → saved | offline | conflict | error`:

- Запись в локальный кэш — сразу при каждом изменении (как сейчас), отправка на
  сервер — debounce 1.5 с, но не реже раза в 10 с при непрерывном редактировании.
- Во время перетаскивания мебели/рисования стены сохранение не стартует до отпускания.
- `pagehide` / `visibilitychange=hidden` → `fetch(..., { keepalive: true })` с
  последним документом (если он ≤ 64 КБ, иначе только локальный кэш + отправка при следующем открытии).
- Нет сети / 5xx → `offline`, экспоненциальный ретрай (2, 4, 8 … 60 с), повтор
  при событии `online`. Изменения не теряются: они в локальном кэше.
- 401 → сессия истекла: локальный кэш сохраняется, открывается окно входа,
  после входа отправка продолжается.
- **Две вкладки одного браузера:** `BroadcastChannel('stylefinder-project')` —
  вкладка, получившая новую ревизию, подхватывает её, если у неё нет несохранённых
  правок; иначе — конфликт.
- **409 (другое устройство):** диалог «Проект изменён в другом месте» с
  вариантами: «Открыть их версию», «Оставить мою (перезаписать)», «Сохранить мою
  копией». Без автоматического слияния.
- Индикатор в шапке шага: «Сохранено», «Сохранение…», «Нет сети — изменения
  сохранены на этом устройстве», «Конфликт», «Не удалось сохранить — повторить».
- Гость видит «Сохранено в этом браузере · Войдите, чтобы не потерять».

### 4.7. Перенос гостевого черновика

После успешного входа или регистрации, если локальный документ не пустой
(есть ответы анкеты, чертёж или расстановка):

- регистрация → черновик **автоматически** становится первым проектом;
- вход → диалог: «Сохранить черновик в аккаунт как новый проект?» [Сохранить] [Удалить черновик] [Позже];
- `POST /projects` с `clientImportId` (uuid, хранится рядом с черновиком) —
  повтор после обрыва сети не создаёт дубль; после 201 локальный черновик
  удаляется, пользователь переходит в новый проект.

### 4.8. Сквозной путь и навигация

Шаги проекта (общий компонент `ProjectStepper` вверху каждого шага):

1. **Стиль** — `/test` (можно пропустить).
2. **Анкета** — `/questionnaire`.
3. **Комната** — `/planner/draw`: нарисовать или «Прямоугольная комната по размерам»
   (шаблон, который сразу строит четыре стены — замена текущей формы размеров в Planner).
4. **Расстановка** — `/planner`: автоматические варианты + ручная правка.
5. **Итог** — существующий финальный экран/экспорт.

Правила:
- шаги доступны в любом порядке после того, как пройдены их зависимости
  (расстановка требует комнату и хотя бы один предмет); пройденные отмечены;
- изменение комнаты после расстановки помечает расстановку устаревшей
  («Комната изменилась — пересчитать?»), а не стирает её молча;
- в чертеже с несколькими помещениями пользователь выбирает одно для расстановки
  (соответствует текущим правилам `drawingBlockingIssues`).

Новые страницы: `/projects` (список, создать, переименовать, дублировать, удалить;
карточка: название, стиль, площадь, этап, дата), `/account`, `/auth/verify`,
`/auth/reset`, `/auth/forgot`, `/privacy`, `/consent`. В навигации — «Мои проекты»
и меню пользователя.

## 6. Тестирование

- **Nest unit:** сессии (хеширование, продление, истечение, отзыв), CSRF-guard,
  токены почты (одноразовость, срок, аннулирование), сервис проектов (владелец,
  ревизии, лимиты, идемпотентность).
- **Nest e2e:** cookie-флаги; изменяющий запрос без `Origin`/заголовка → 403;
  чужой проект → 404 на всех методах; 409 при старой ревизии; forgot-password
  одинаков для существующего и несуществующего email; удаление аккаунта каскадом.
- **Next unit:** миграции v1–v4 → v5 (включая подтягивание editor-session),
  машина автосохранения на фейковых таймерах (debounce, ретраи, offline, 401, 409),
  перенос гостевого черновика без дублей.
- **Playwright:**
  1. гость проходит тест → анкету → рисует → расставляет → регистрируется → проект в списке, всё на месте;
  2. письмо подтверждения из Mailpit → почта подтверждена;
  3. «забыл пароль» → новый пароль → старая сессия в другом контексте выкинута;
  4. офлайн во время правки → индикатор → сеть вернулась → сохранено, после перезагрузки на месте;
  5. две вкладки → правка в одной видна в другой; одновременная правка → конфликт-диалог;
  6. другой пользователь не открывает чужой `?project=`;
  7. удаление аккаунта → вход невозможен, проекты недоступны.

## 7. Решения по открытым вопросам (согласовано 2026-10-20)

1. Мебель расставляется только на шаге «Расстановка»; редактор мебели в
   `/planner/draw` из пользовательского пути убирается.
2. Старая форма размеров в Planner заменяется шаблоном «Прямоугольная комната»
   на шаге «Комната».
3. Лимиты: 50 проектов на пользователя, 1 МБ на документ проекта.
4. Проект удаляется сразу и навсегда, после подтверждения.
5. Неподтверждённые аккаунты без входов 30 дней удаляются.

Идеи интерфейса берём из RemPlanner (как уже сделано для редактора комнаты),
не копируя его бренд и контент.
